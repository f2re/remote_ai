# Release pipeline

Remote AI ships through GitHub Actions. Release builds are Universal 2 and are verified before publication.

## CI

Pull requests and pushes to `main` run one macOS verification job:

1. `swift test --parallel`
2. native `swift build -c release`
3. `./build.sh` to package a Universal 2 (`arm64` + `x86_64`) `.app`
4. `./tools/snap.sh` to render the deterministic 16-image light/dark screenshot set
5. `./tools/verify-release.sh` to verify bundle metadata, codesign, architectures, and screenshots
6. ZIP integrity checks and SHA-256 generation
7. upload of the app ZIP, screenshot ZIP, checksums, and individual PNGs as one verified candidate artifact

CI uses read-only repository permissions and cancels superseded pull-request or `main` runs. Feature-branch pushes do not run a second duplicate Universal build once a PR exists. `release/**` branches are validated by the dedicated Release workflow.

## Dry-run release

Push a normal `release/**` branch that does not match `release/publish-v*`, or run the **Release** workflow manually with a version such as `0.2.0`.

The workflow repeats the full release gate, creates the application ZIP and screenshot ZIP, writes SHA-256 checksums, and uploads the complete release candidate. A normal release branch or manual dry run does not create a GitHub Release.

## Publish — preferred path

Publish from the current green `main` by creating a branch named `release/publish-vMAJOR.MINOR.PATCH` and pushing a marker commit:

```bash
git switch main
git pull --ff-only
git switch -c release/publish-v0.2.0
git commit --allow-empty -m "release: publish v0.2.0"
git push -u origin release/publish-v0.2.0
```

The Release workflow then performs the complete publication transaction in one job:

1. verifies that the publish branch is based on the current `main`
2. checks out that exact `main` commit, not the marker commit
3. runs tests and builds the final version
4. packages and verifies the Universal 2 app
5. renders and verifies all release screenshots
6. performs optional Developer ID signing/notarization
7. creates or validates the immutable `vMAJOR.MINOR.PATCH` tag on the verified `main` commit
8. publishes the GitHub Release and all assets

Keeping tag creation and publication in the same verified job is intentional: GitHub does not recursively start another Actions workflow for events generated by the repository `GITHUB_TOKEN`.

## Publish — external tag path

A manually created external `v*` tag is also supported:

```bash
git switch main
git pull --ff-only
git tag v0.2.0
git push origin v0.2.0
```

The workflow rejects a tag if its target is not contained in `main` and then runs the same release gate.

A successful publication attaches:

- `RemoteAI-<version>-macOS.zip`
- `RemoteAI-<version>-screenshots.zip`
- `SHA256SUMS.txt`
- all individual light/dark release PNGs

If Apple signing/notarization secrets are absent, the app is ad-hoc signed and the GitHub Release is automatically marked as a prerelease. The binary is still codesign-verified and Universal 2, but users may encounter Gatekeeper friction.

## Developer ID signing and notarization

Configure these GitHub Actions secrets:

- `MACOS_CERTIFICATE_P12`: base64-encoded Developer ID Application `.p12`
- `MACOS_CERTIFICATE_PASSWORD`: password for the `.p12`
- `APPLE_ID`: Apple ID used by `notarytool`
- `APPLE_TEAM_ID`: Apple Developer Team ID
- `APPLE_APP_PASSWORD`: app-specific password

With all secrets present the workflow:

1. imports the Developer ID certificate into an ephemeral keychain
2. signs the Universal 2 app with hardened runtime and timestamp
3. verifies the bundle and release screenshots
4. submits the application ZIP to Apple notary service
5. staples and validates the ticket
6. runs `spctl --assess`
7. verifies the stapled app again
8. republishes the final ZIP and creates a normal (non-prerelease) GitHub Release

Secrets are never stored in the repository.

## Versioning

`Resources/Info.plist` keeps the development baseline version. During CI/CD, `APP_VERSION` and `BUILD_NUMBER` override `CFBundleShortVersionString` and `CFBundleVersion` in the packaged app without modifying the source plist.

`tools/verify-release.sh` rejects a package if the resulting bundle version differs from the requested release version.
